# Feature Specification: Enable Query Caching by Removing Complex Input Arguments

**Feature Branch**: `001-graphql-query-caching`

**Created**: 2026-08-20

**Status**: Draft

**Input**: User description: "[JS SDK] Enable query caching by removing complex input arguments — replace complex input objects with simple scalar values to make queries deterministic and cacheable"

## Clarifications

### Session 2026-08-20

- Q: Which query types are in scope — content only or all? → A: All query types generated by the SDK.
- Q: Should filter ordering be normalized for deterministic caching? → A: Yes, normalize filter ordering (e.g., alphabetical by field name).
- Q: Should developers be able to opt out of stored queries? → A: Yes, allow opt-out via a query option (default remains `stored=true`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Query with Simple Scalar Variables (Priority: P1)

As a developer using the JS SDK, I want all 5 `_Content`-based query types to use simple scalar variables instead of complex input objects so that the query definitions are deterministic and can be cached/reused by the system.

**Why this priority**: This is the core change — all other improvements (caching, performance) depend on queries being refactored to use scalar inputs instead of complex nested objects.

**Independent Test**: Can be tested by issuing a content retrieval query and verifying that the generated query uses simple scalar variables (e.g., `$key: String`) rather than complex input types (e.g., `$where: _ContentWhereInput`), and that the query returns the same results as before.

**Acceptance Scenarios**:

1. **Given** a content retrieval request with filter criteria, **When** the SDK generates the query, **Then** the query variables use only simple scalar values (strings, numbers, booleans) — no complex input objects like `_ContentWhereInput` or `VariationInput`.
2. **Given** a content retrieval request with nested filter criteria, **When** the SDK generates the query, **Then** the filter conditions are inlined into the static query definition rather than passed as dynamic structured variables.
3. **Given** a query previously using complex input arguments, **When** the same content is requested with the new approach, **Then** the results are functionally identical to the previous implementation.

---

### User Story 2 - Stored and Cached Queries (Priority: P1)

As a developer using the JS SDK, I want queries to be registered, stored, and reusable so that the system avoids repeated query parsing and translation overhead on every request.

**Why this priority**: Query caching is the primary business value — reduced latency and processing overhead directly impacts end-user experience.

**Independent Test**: Can be tested by issuing the same content query multiple times and verifying that the query definition is reused (stored) rather than regenerated, and that `stored=true` is present in the query string by default.

**Acceptance Scenarios**:

1. **Given** a content query that has been issued before, **When** the same query is issued again, **Then** the system reuses the stored query definition without regenerating or re-translating it.
2. **Given** any content query generated by the SDK, **When** the query is sent, **Then** it includes `stored=true` by default to enable server-side query caching.
3. **Given** two identical content retrieval requests, **When** the SDK generates queries for both, **Then** the generated query strings are identical (deterministic output).

**Why this priority**: Ensuring backward compatibility protects existing users from breaking changes and builds confidence in upgrading.

**Independent Test**: Can be tested by running the existing content retrieval test suite and verifying all scenarios pass with the new query generation approach.

**Acceptance Scenarios**:

**Why this priority**: Performance improvement is the ultimate outcome that delivers end-user value, but it depends on the query restructuring (P1 stories) being in place first.

**Independent Test**: Can be tested by measuring query processing latency before and after the change and verifying measurable improvement.

**Acceptance Scenarios**:

### Edge Cases

- What happens when a query has no filter criteria at all (empty/null filters)?
- How does the system handle queries with a very large number of filter conditions that would produce very long static query strings?
- What happens when the same content is queried with slightly different filter orderings? (Resolved: filters are normalized by field name ordering, so logically equivalent queries produce identical strings.)
- How does the system behave when cached/stored queries become stale due to schema changes?
- How does the metadata discovery query (`GET_CONTENT_METADATA_QUERY`) handle the transition? This query runs before the main content query to discover the content type name, and it also uses `_ContentWhereInput`. See Technical Design section for resolution.
- How does the preview flow interact with stored queries, given that preview always disables HTTP cache (`?cache=false`) and uses different auth (Bearer token)?
- How does multi-site host filtering affect query shapes? (Resolved: two static query variants — with-host and without-host — are generated for path-based queries. See Technical Design section 3.)
- `GET_ITEMS_QUERY` currently uses the wrong GraphQL operation name `GetPath` (copy-paste bug). This must be fixed to `GetItems` before implementing stored queries to avoid name collisions.

## Technical Design

### Query Types in Scope

The SDK generates 5 distinct query types that all use `_ContentWhereInput` and must be converted. Each has different filter structures:

#### 1. `GET_CONTENT_METADATA_QUERY` (metadata discovery)

Every content retrieval starts with this query to discover the content type name. It uses `_ContentWhereInput` for filtering.

- **Current**: `query GetContentMetadata($where: _ContentWhereInput, $variation: VariationInput) { ... }`
- **Target**: Inline filter structure, use scalar variables for values only:
  ```graphql
  query GetContentMetadata($key: String) {
    _Content(where: { _metadata: { key: { eq: $key } } }) { ... }
  }
  ```
- **Note**: This query is a prerequisite for generating the main content query (it discovers the content type). Since its structure is already static (always filters by key/path/version), it can be converted independently — no chicken-and-egg problem. Multiple variants of this query will exist (by-key, by-path, by-preview) with different inlined filter structures.

#### 2. `generateSingleContentQuery` (single content by key)

Used by `getContent()` and `getPreviewContent()`.

- **Current**: `query GetContent($where: _ContentWhereInput, $variation: VariationInput) { ... }`
- **Target**:
  ```graphql
  query GetContent($key: String) {
    _Content(where: { _metadata: { key: { eq: $key } } }) { ... }
  }
  ```
- **Preview variant** (needs key + version + locale):
  ```graphql
  query GetPreviewContent($key: String, $version: String, $locale: String) {
    _Content(where: { _metadata: { key: { eq: $key }, version: { eq: $version }, locale: { eq: $locale } } }, variation: ALL) { ... }
  }
  ```

#### 3. `generateMultipleContentQuery` (content by path)

Used by `getContentByPath()`. The current `pathFilter` builds an `_or` with 4 conditions (with/without trailing slash × default/hierarchical URL).

- **Current**: Complex `_or` array passed via `$where: _ContentWhereInput`
- **Target (without host)**: Inline the `_or` structure, use scalar variables for path values:
  ```graphql
  query GetContentByPath($path: String, $pathNoSlash: String) {
    _Content(where: { _or: [
      { _metadata: { url: { default: { eq: $path } } } },
      { _metadata: { url: { default: { eq: $pathNoSlash } } } },
      { _metadata: { url: { hierarchical: { eq: $path } } } },
      { _metadata: { url: { hierarchical: { eq: $pathNoSlash } } } }
    ] }) { ... }
  }
  ```
- **Target (with host, for multi-site)**: When a `host` is configured, each condition adds a `base` filter:
  ```graphql
  query GetContentByPathWithHost($path: String, $pathNoSlash: String, $host: String) {
    _Content(where: { _or: [
      { _metadata: { url: { default: { eq: $path }, base: { eq: $host } } } },
      { _metadata: { url: { default: { eq: $pathNoSlash }, base: { eq: $host } } } },
      { _metadata: { url: { hierarchical: { eq: $path }, base: { eq: $host } } } },
      { _metadata: { url: { hierarchical: { eq: $pathNoSlash }, base: { eq: $host } } } }
    ] }) { ... }
  }
  ```
- **Note**: The `_or` structure is static (always 4 conditions with the same shape) — only the path/host values are dynamic. Two static query shapes are needed: with-host and without-host.

#### 4. `GET_PATH_QUERY` (breadcrumb/ancestors)

- **Current**: `query GetPath($where: _ContentWhereInput, $locale: [Locales]) { ... }`
- **Target**:
  ```graphql
  query GetPath($key: String, $locale: [Locales]) {
    _Content(where: { _metadata: { key: { eq: $key } } }, locale: $locale) { ... }
  }
  ```

#### 5. `GET_ITEMS_QUERY` (child pages)

- **Current**: `query GetItems($where: _ContentWhereInput, $locale: [Locales]) { ... }` *(Note: current code incorrectly uses operation name `GetPath` — must be fixed to `GetItems`)*
- **Target**:
  ```graphql
  query GetItems($key: String, $locale: [Locales]) {
    _Content(where: { _metadata: { key: { eq: $key } } }, locale: $locale) { ... }
  }
  ```

### Handling Non-Scalar Types: `variation` and `locale`

The current codebase uses two types that are not simple scalars:

#### `VariationInput` (discriminated union)

Current type: `{ include: 'NONE' }` | `{ include: 'ALL' }` | `{ include: 'SOME', value: string[], includeOriginal?: boolean }`

**Approach**: Instead of passing `VariationInput` as a variable, inline the variation mode into the static query definition and only pass values as scalars when needed:

- `include: 'NONE'` → omit `variation` from query entirely
- `include: 'ALL'` → inline `variation: ALL` in the query string (no variable needed)
- `include: 'SOME'` → this requires generating a query variant with `variation: { include: SOME, value: [$v1, $v2, ...] }` where each value is a scalar `String` variable. The number of variation values determines the query shape, so different counts produce different (but still static) query definitions.

#### `locale` (enum array)

Current type: `[Locales]` (array of locale enums)

**Approach**: Keep `$locale: [Locales]` as-is — the `Locales` enum is already a scalar-like type, and the array wrapper is a standard GraphQL list type (not a complex input object). This preserves multi-locale support and backward compatibility. No conversion needed.

### Relationship to Existing Caching Mechanisms

The codebase currently has two caching layers. The new `stored=true` mechanism is a **third, independent layer**:

| Layer | Mechanism | Scope | Stays? |
|-------|-----------|-------|--------|
| **Client-side query string cache** | `withQueryCaching()` in `cache.ts` — memoizes generated query strings by content type in a `Map<string, string>` | Avoids regenerating the same query string within the same client instance | **Yes** — still valuable for avoiding repeated fragment generation. Unaffected by this change. |
| **HTTP cache control** | `?cache=true/false` URL parameter | Controls server-side HTTP response caching | **Yes** — remains as-is. Preview requests continue to use `?cache=false`. |
| **Stored query (NEW)** | `stored=true` in query string | Tells the GraphQL processing layer to store the pre-processed query plan for reuse across requests | **New** — this is the primary deliverable of this feature. |

These three layers are complementary:
- `withQueryCaching()` avoids regenerating the query string client-side.
- `stored=true` avoids re-parsing and re-translating the query server-side.
- `?cache=true` avoids re-executing the query for identical requests.

### `stored=true` Mechanism

The `stored=true` flag MUST be appended as a **URL query parameter** on the GraphQL endpoint, consistent with the existing `?cache=true` pattern:

```
https://graph.optimizely.com/content/v2?cache=true&stored=true
```

This can be controlled per-request via `GraphQueryOptions`:
- Default: `stored=true` (enabled)
- Opt-out: developer passes `{ stored: false }` in query options

### Preview Flow Behavior

Preview requests have special requirements:
- **HTTP cache**: Always `?cache=false` (unchanged — preview must always fetch fresh data)
- **Stored query**: `stored=true` is still applied — the query *definition* can be reused server-side even though the query *results* are not cached
- **Auth**: Uses `Bearer <previewToken>` instead of `epi-single <apiKey>` (unchanged)
- **Variation**: Preview always uses `variation: ALL` (inlined in the static query definition)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST generate all 5 `_Content`-based query types (`GET_CONTENT_METADATA_QUERY`, `generateSingleContentQuery`, `generateMultipleContentQuery`, `GET_PATH_QUERY`, `GET_ITEMS_QUERY`) using only simple scalar variable types (strings, numbers, booleans, and GraphQL enums like `Locales`) — no complex input objects such as `_ContentWhereInput` or nested filter inputs.
- **FR-002**: System MUST produce deterministic query definitions — identical requests MUST generate identical query strings. Filter conditions MUST be normalized by field name ordering to ensure logical equivalence produces string equivalence.
- **FR-003**: System MUST support query registration and storage so that pre-processed query definitions can be reused without repeated generation.
- **FR-004**: System MUST enable stored queries by default by appending `stored=true` as a URL query parameter on the GraphQL endpoint (e.g., `?cache=true&stored=true`). System MUST provide a query option for developers to opt out of stored queries (set `stored=false`) on a per-request basis via `GraphQueryOptions`.
- **FR-005**: System MUST return functionally identical results as the current implementation for all existing retrieval scenarios across all query types.
- **FR-006**: System MUST inline filter conditions into the static query definition rather than passing them as dynamically structured variable objects.
- **FR-007**: System MUST produce queries that are eligible for server-side caching by the query processing layer.
- **FR-008**: System MUST update all documentation and examples to reflect the new query patterns.
- **FR-009**: System MUST convert all 5 query types (`GET_CONTENT_METADATA_QUERY`, `generateSingleContentQuery`, `generateMultipleContentQuery`, `GET_PATH_QUERY`, `GET_ITEMS_QUERY`) to use inlined filter structures with scalar variables. Multiple static variants of each query type MAY exist to cover different filter shapes (e.g., by-key, by-path, by-preview, with-host, without-host).
- **FR-010**: System MUST handle `VariationInput` by inlining the variation mode (`ALL`, `NONE`) into the static query definition, and using scalar `String` variables for `SOME` variation values. Each distinct count of `SOME` values produces a different static query shape and cache entry.
- **FR-011**: System MUST preserve multi-locale support by keeping `$locale: [Locales]` (array of enum values). No conversion needed — `Locales` enum is already a scalar-like type.
- **FR-013**: System MUST fix `GET_ITEMS_QUERY` operation name from `GetPath` to `GetItems` to prevent stored query name collisions.
- **FR-014**: System MUST remove unused `variationFilter()` function from `filters.ts` as part of dead code cleanup.
- **FR-012**: Preview requests MUST use `stored=true` for query definition reuse but MUST keep HTTP cache disabled (`?cache=false`) to ensure fresh preview data.

### Key Entities

- **Query Definition**: A structured representation of a content query including its static shape, variable declarations, and filter conditions. Key attributes: query string, variable types, stored flag, content type target.
- **Query Variable**: A named parameter within a query definition. In the new model, variables are limited to simple scalar types (string, number, boolean) rather than complex input objects.
- **Stored Query**: A previously registered query definition that can be retrieved and reused without re-generation. Key attributes: query identifier, query string, creation timestamp, usage count.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of generated content queries use only simple scalar variables — zero queries use complex input objects.
- **SC-002**: Repeated identical content requests reuse stored query definitions rather than regenerating them.
- **SC-003**: All existing content retrieval scenarios continue to return correct results without modification by the consuming application.
- **SC-004**: Query processing latency for repeated queries is reduced by at least 50% compared to the current implementation. Measurement methodology: compare server-side query processing time (from GraphQL response headers or server logs) for the same content query issued 10 times — measure average latency of requests 2–10 (excluding cold first request) between old (complex input) and new (stored/scalar) approaches.
- **SC-005**: Documentation and examples are fully updated to demonstrate the new query patterns, with no references to the deprecated complex input approach.

## Assumptions

- The query processing layer (server-side) already supports stored/cached queries when `stored=true` is provided — no server-side changes are required.
- The set of content query types currently in use is finite and well-known, making it feasible to convert all of them to scalar-based patterns.
- Filter conditions can be represented as inline static values within the query definition without exceeding practical query string length limits for typical use cases.
- Existing consumers of the SDK interact through the SDK's public API, not by constructing raw queries directly — so changing the query format does not break consumer code.
- Performance improvements come from avoiding repeated query parsing and translation (complex input to search engine query), not from changes to the search engine itself.
