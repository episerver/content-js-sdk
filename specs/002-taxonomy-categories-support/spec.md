# Feature Specification: CMS Taxonomy Categories Support

**Feature Branch**: `feature/CMS-56217-Support-CMS-Taxonomy-categories`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "Support CMS Taxonomy categories in @optimizely/cms-sdk — always include categories in the `ItemMetadata` fragment of generated queries, support category hierarchy resolution (resolve parent/taxonomy hierarchy without a separate _TaxonomyTerm query)."

## Clarifications

### Session 2026-09-23

- Q: What shape should the resolved category hierarchy take on the SDK response type? → A: Flat breadcrumb array — each resolved category is an object with `uri` (term URI), `name` (localized label), and `path` (full breadcrumb array from root to the term itself, each with `uri` and `name`). The `path` array always includes the term itself as the last element — the top-level `uri` and `name` are convenience accessors equivalent to `path[path.length - 1]`.
- Q: Should category hierarchy resolution be always-on or opt-in via a query option? → A: Opt-in via a query option (e.g., `resolveCategories: true`). Raw `categories` URIs are always included; hierarchy resolution is enabled explicitly when needed.
- Q: How should the SDK handle CMS instances whose Graph schema does not include taxonomy fields? → A: Graceful omission — the SDK detects whether the Graph schema supports taxonomy (via `TaxonomyMode` schema probing) and silently omits the `categories` field from the `ItemMetadata` fragment if not supported, returning `undefined` for categories on the response.
- Q: Should resolved category hierarchy labels be localized to match the content item's locale? → A: Yes — category labels are returned in the same locale as the content item being fetched. If a category term has no translation for the requested locale, the SDK returns the term's default-locale label as fallback.
- Q: Where does `categories` appear in the SDK's TypeScript types? → A: Two layers must be updated: **(1) GraphQL layer** — the `categories` field is added to the `ItemMetadata` fragment in `baseTypeUtil.ts` (alongside `changeset` and `displayOption`), which is spread into `_metadata` via the `IContentMetadata` fragment chain. **(2) TypeScript layer** — `InferredItemMetadata` in `infer.ts` is extended with `categories: string[] | undefined`. This is flattened into `_metadata` via `Partial<InferredItemMetadata>`, following the existing pattern for `changeset` and `displayOption`. Developers access raw categories as `_metadata.categories`. Note: `resolvedCategories` does NOT go on `InferredItemMetadata` — it is SDK-side augmentation, not a GraphQL field. The type mechanism for surfacing it on `_metadata` should be decided during planning.
- Q: How should schema detection for taxonomy work? → A: Follow the existing `DamMode` tri-state pattern (`'automatic' | 'on' | 'off'`) with a `TaxonomyMode` option. In `'automatic'` mode (default), the SDK probes the Graph schema via an introspection query (e.g., `__type(name: "_TaxonomyTerm")`) to detect taxonomy support. When detected or forced `'on'`, the `ItemMetadata` fragment includes `categories`; when `'off'` or not detected, it is omitted. When forced `'on'` but the schema does not support taxonomy, the Graph API will return an error — this is the same behavior as `DamMode: 'on'` on a non-DAM instance, and is the developer's responsibility to handle.
- Q: Where does `resolveCategories` live in the API? → A: `resolveCategories` is a boolean option on the operations layer (passed to `getContent`, `getContentByPath`, `getPreviewContent` etc. in the options bag — specifically on `GraphGetItemOptions` and `GraphGetContentOptions`, NOT on the base `GraphQueryOptions` which also covers `getLinks` where it would be irrelevant), NOT on `GraphFragmentOptions`. This is because hierarchy resolution may require a separate batched query after the content query returns, which is orchestrated in `operations.ts` — it is not purely a fragment/query-generation concern.
- Q: What is the response shape difference between resolved and unresolved categories? → A: `_metadata.categories` is always `string[] | undefined` (raw term URIs — empty array `[]` when content has no categories assigned, `undefined` when taxonomy is not supported at schema level). When `resolveCategories: true`, an additional `_metadata.resolvedCategories` property is populated as `ResolvedCategory[] | undefined`, where each `ResolvedCategory` has `{ uri, name, path }`. This avoids union types on a single property and keeps the API additive — consumers who only need URIs never need to deal with objects.
- Q: What happens when `resolveCategories: true` but taxonomy is not available? → A: If `TaxonomyMode` resolves to disabled (either `'off'` or `'automatic'` with no taxonomy detected), `resolveCategories` is silently ignored — `_metadata.categories` is `undefined` and `_metadata.resolvedCategories` is `undefined`, no error is thrown. Similarly, if the hierarchy resolution mechanism is unavailable (neither inline parent fields nor batched `_TaxonomyTerm` query supported), the SDK logs a warning and returns `resolvedCategories: undefined`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Fetch Content with Categories (Priority: P1)

As a developer building a front end with `@optimizely/cms-sdk`, I want content fetched through the SDK to automatically include the taxonomy categories assigned to it in Optimizely SaaS CMS, so that I can render, filter, and route on categories without manually patching the generated GraphQL query.

**Why this priority**: This is the core capability — without it, SDK consumers have no access to category data at all. Every other story depends on categories being present in the query response.

**Independent Test**: Fetch any content item via `createSingleContentQuery` or `createMultipleContentQuery` and verify that the response includes `_metadata.categories` as a typed array of category term URIs, with no manual query patching required.

**Acceptance Scenarios**:

1. **Given** a content item with one or more categories assigned in CMS, **When** the developer fetches that item via the SDK's standard single-content method, **Then** the response includes `_metadata.categories` as a typed array of category term URI strings.
2. **Given** a content item with one or more categories assigned in CMS, **When** the developer fetches multiple items via the SDK's standard multiple-content method, **Then** each item in the response includes `_metadata.categories` as a typed array of category term URI strings.
3. **Given** a content item with no categories assigned, **When** the developer fetches that item via any standard SDK method, **Then** `_metadata.categories` is present as an empty array `[]` and does not cause an error.
4. **Given** an existing SDK consumer who has not changed their code, **When** they upgrade to the new SDK version, **Then** their existing content queries continue to work without breaking changes — the additional `categories` field is additive only.

---

### User Story 2 - Category Hierarchy Resolution (Priority: P2)

As a developer, I want to opt in to resolving the parent/taxonomy hierarchy for each category term URI returned in `_metadata.categories`, so that I can display breadcrumb paths, build category trees, or filter by parent categories without issuing a separate `_TaxonomyTerm` GraphQL query.

**Why this priority**: Raw category term URIs alone have limited display value. Developers need the hierarchy (parent terms, labels) to build meaningful category navigation, breadcrumbs, and filtered views. Resolving this within the SDK eliminates a common boilerplate query.

**Independent Test**: Fetch a content item with `resolveCategories: true` that has categories assigned at multiple levels of a taxonomy tree and verify that `_metadata.resolvedCategories` includes resolved hierarchy information as a flat breadcrumb array for each category.

**Acceptance Scenarios**:

1. **Given** a content item assigned to a category nested 2+ levels deep, **When** the developer fetches that item with hierarchy resolution enabled, **Then** `_metadata.resolvedCategories` contains an entry for each category, each with a `path` array ordered root-to-leaf including the term itself as the last element (e.g., for a content item assigned to "Nordic": `{ uri: "nordic-uri", name: "Nordic", path: [{ uri: "region-uri", name: "Region" }, { uri: "europe-uri", name: "Europe" }, { uri: "nordic-uri", name: "Nordic" }] }`).
2. **Given** a content item assigned to multiple categories across different taxonomy trees, **When** the developer fetches that item with hierarchy resolution enabled, **Then** each entry in `_metadata.resolvedCategories` has its own independent `path` breadcrumb array.
3. **Given** a content item assigned to a root-level category (no parent), **When** the developer fetches that item with hierarchy resolution enabled, **Then** the `path` array contains a single element — the root term itself (e.g., `{ uri: "root-uri", name: "Root", path: [{ uri: "root-uri", name: "Root" }] }`).
4. **Given** a content item fetched WITHOUT hierarchy resolution enabled, **When** the developer accesses `_metadata`, **Then** `_metadata.categories` contains raw URIs and `_metadata.resolvedCategories` is `undefined` (no hierarchy data, no extra network cost).
5. **Given** hierarchy resolution is enabled, **When** the developer inspects network requests, **Then** the hierarchy data is obtained within the existing content query (if the Graph API supports inline taxonomy parent fields) or via a single batched `_TaxonomyTerm` query for all category URIs — no N+1 per-term queries are issued.
6. **Given** a multilingual CMS instance, **When** the developer fetches content in a specific locale with hierarchy resolution enabled, **Then** category labels in the `path` array are returned in the same locale as the content item. If a term has no translation for the requested locale, the default-locale label is returned as fallback.

---

### User Story 3 - Typed Category Data on SDK Content Types (Priority: P1 — implemented with Stories 1 & 2, tested separately)

As a developer using TypeScript, I want `_metadata.categories` and `_metadata.resolvedCategories` to be properly typed in the SDK's content type definitions, so that I get autocompletion and type safety when accessing category information.

**Why this priority**: Type changes (`InferredItemMetadata`, `ResolvedCategory`) are inseparable from Stories 1 and 2 — the code that adds `categories` to the fragment must also add the type. This story is listed separately for independent testability (autocompletion, compiler enforcement), but it is implemented in the same PRs as Stories 1 and 2, not deferred.

**Independent Test**: In a TypeScript project consuming the SDK, access `_metadata.categories` and `_metadata.resolvedCategories` on a fetched content item and verify that the IDE provides autocompletion and the compiler enforces the correct types without requiring any cast.

**Acceptance Scenarios**:

1. **Given** a TypeScript project using the SDK, **When** the developer accesses `_metadata.categories` on a fetched content item, **Then** TypeScript autocompletion suggests `categories` and its type is `string[] | undefined` (not `any`).
2. **Given** the resolved hierarchy data from Story 2, **When** the developer accesses `_metadata.resolvedCategories[0].name` or `_metadata.resolvedCategories[0].path[0].name`, **Then** TypeScript types are correct and no `as` cast is needed. The type of `resolvedCategories` is `ResolvedCategory[] | undefined`.
3. **Given** a `ResolvedCategory` type, **Then** it is exported from the SDK's public API with the shape `{ uri: string; name: string | null; path: Array<{ uri: string; name: string | null }> }`.

### Edge Cases

- **No taxonomy trees configured**: The CMS instance has taxonomy enabled but no trees. `_metadata.categories` returns an empty array `[]`, with no error. When `resolveCategories: true`, `_metadata.resolvedCategories` is an empty array `[]` (no categories to resolve).
- **Taxonomy feature not enabled (schema-level)**: The CMS instance's Graph schema does not include taxonomy fields at all. The SDK detects this via `TaxonomyMode` schema probing (`'automatic'` mode) and gracefully omits the `categories` selection from the `ItemMetadata` fragment — `_metadata.categories` is `undefined` on the response, no query error occurs. This is distinct from "no categories assigned" (data-level), where `categories` would be an empty array.
- **`TaxonomyMode: 'on'` but schema doesn't support taxonomy**: The SDK includes `categories` in the fragment regardless. The Graph API will return a query error. This follows the same behavior as `DamMode: 'on'` on a non-DAM instance — it is the developer's responsibility to ensure the mode matches the instance capabilities.
- **Deleted or moved taxonomy term**: A category term URI points to a term that has been deleted or moved. The SDK returns what the Graph API provides without crashing. If hierarchy resolution is enabled and resolution fails for a specific term, that term's entry in `resolvedCategories` has `name: null` and `path: [{ uri: "<original-uri>", name: null }]` (single-element array with the term itself) rather than causing the entire fetch to fail. This preserves the invariant from FR-005 that `path` always includes the term itself as the last element — the only difference is `name: null`. Note: this means the `ResolvedCategory` type uses `name: string | null` to accommodate unresolvable terms.
- **Batched hierarchy query network failure**: If the entire batched `_TaxonomyTerm` query fails (network error, timeout, etc.), the SDK does NOT throw — it logs a warning and returns `_metadata.resolvedCategories` as `undefined`. The content data itself (`_metadata.categories` with raw URIs) remains intact.
- **Very deep taxonomy hierarchies (10+ levels)**: The SDK handles arbitrary depth. If hierarchy resolution uses inline query extension, the query depth is bounded by the Graph API's own limits. If using a batched `_TaxonomyTerm` query, depth is not a concern since the API returns the full path.
- **Large number of categories (50+)**: The SDK does not introduce N+1 query problems. Hierarchy resolution is batched (single `_TaxonomyTerm` query for all URIs) or embedded in the content query.
- **Locale fallback for category labels**: When hierarchy resolution is enabled and a term has no translation for the requested locale, the SDK returns the term's default-locale label as fallback (matching Graph API behavior).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The SDK MUST include `categories` in the `ItemMetadata` GraphQL fragment (alongside `changeset` and `displayOption` in `baseTypeUtil.ts`, spread into `_metadata` via the `IContentMetadata` fragment chain) for every query generated by `createSingleContentQuery` and `createMultipleContentQuery` — enabled by default via automatic schema detection, following the `DamMode` tri-state pattern (`TaxonomyMode: 'automatic' | 'on' | 'off'`). Note: Forms does not use a tri-state option — it is always auto-detected and resolved to `formsEnabled: boolean` without a user-facing mode. `TaxonomyMode` follows `DamMode`'s pattern: `TaxonomyMode` (type in `options.ts`) → `taxonomy` (option field on `GraphFragmentOptions`) → `taxonomyEnabled` (resolved boolean on `QueryContext`). In `'automatic'` mode (default), the SDK probes the Graph schema and includes the field only when taxonomy is supported. When forced `'on'` on a non-taxonomy instance, the Graph API will error (same as `DamMode: 'on'` on a non-DAM instance). The raw categories are exposed on the SDK's `_metadata.categories` property as `string[] | undefined`, consistent with how `changeset` and `displayOption` from `InferredItemMetadata` are flattened into `_metadata`.
- **FR-002**: The `categories` field MUST be typed as `string[] | undefined` on `InferredItemMetadata` in `infer.ts`. This is flattened into `_metadata` via `Partial<InferredItemMetadata>`, following the existing pattern for `changeset` and `displayOption`.
- **FR-003**: Content with no categories assigned MUST return an empty array `[]` for `_metadata.categories` — it MUST NOT cause a runtime error or schema validation failure. When taxonomy is not supported at the schema level (`TaxonomyMode: 'automatic'` and not detected), `_metadata.categories` is `undefined` (field not selected in the query). These are distinct behaviors: empty array `[]` = data-level (no categories assigned); `undefined` = schema-level (taxonomy not available). The value is never `null`.
- **FR-004**: The SDK MUST provide an opt-in option `resolveCategories: true` on the operations layer (options bag for `getContent`, `getContentByPath`, `getPreviewContent` in `operations.ts` — specifically on `GraphGetItemOptions`, `GraphGetContentOptions`, and a new `GraphGetPreviewOptions` type replacing the bare `GraphQueryOptions` currently used by `getPreviewContent`), NOT on `GraphFragmentOptions` or `GraphQueryOptions` (which is also the base type for `GraphGetLinksOptions`, where `resolveCategories` is not applicable). This is because hierarchy resolution may require a post-query step (separate batched query) orchestrated in the operations layer. When enabled, the SDK populates `_metadata.resolvedCategories` as `ResolvedCategory[] | undefined`. When not enabled, `_metadata.resolvedCategories` is `undefined` and no extra network cost is incurred. `_metadata.categories` (raw URIs) is always present regardless of this option. When `resolveCategories: true` but taxonomy is not available (either `TaxonomyMode: 'off'` or `'automatic'` with no taxonomy detected), the option is silently ignored — `resolvedCategories` is `undefined`, no error is thrown. **`undefined` semantics**: From the consumer's perspective, `resolvedCategories: undefined` means "resolved data is not available" — consumers MUST NOT distinguish between causes (option not set, taxonomy unavailable, resolution mechanism missing, or batch query failure). The SDK uses internal logging (warnings) to surface the cause for debugging; the public API intentionally collapses all non-available states into `undefined`. **Important**: `resolvedCategories` is NOT a GraphQL field — it is always SDK-side augmentation. Regardless of the data source (inline parent fields embedded in the content query, or a separate batched `_TaxonomyTerm` query), the SDK constructs `resolvedCategories` in the operations layer and attaches it to the response. It never appears in fragment definitions or generated GraphQL types. **1:1 invariant**: When `resolvedCategories` is not `undefined`, it MUST contain exactly one `ResolvedCategory` entry for each URI in `_metadata.categories`, in the same order. Resolution failure for an individual term does NOT remove its entry — see FR-005 for the `name: null` fallback shape.
- **FR-005**: When hierarchy resolution is enabled, each resolved category MUST be returned as a `ResolvedCategory` object: `{ uri: string; name: string | null; path: Array<{ uri: string; name: string | null }> }`, where `path` is the full breadcrumb from root to the term itself (the term is the last element of `path`; top-level `uri`/`name` are convenience accessors equivalent to `path[path.length - 1]`). **Why `name: string | null`**: `null` is chosen (over `undefined`) to distinguish "the term exists but its name could not be resolved" (deleted/moved term — `null`) from "resolved data is not available at all" (`resolvedCategories: undefined`). This follows the JSON convention where `null` is an explicit "no value" signal, whereas `undefined` means "field not present." Consumers who only work with live terms can narrow the type with a simple `if (category.name !== null)` guard. **Implementation mechanism (to be confirmed during planning)**: The preferred approach is to extend the content GraphQL query to inline taxonomy parent fields if the Graph API supports selecting parent/ancestor data on `categories`. If not supported, the fallback is a single batched `_TaxonomyTerm` query for all unique category URIs in the content response. If neither mechanism is available, the SDK MUST log a warning and return `resolvedCategories: undefined` (silently degrade, not throw). **Prerequisite**: The planning phase MUST inspect the Graph schema to determine which mechanism is available, before implementation begins.
- **FR-006**: Hierarchy resolution MUST NOT introduce N+1 query problems — it MUST use batching (single query for all URIs) or embed the hierarchy data within the content query.
- **FR-007**: Existing SDK consumers MUST NOT experience breaking changes — the addition of `categories` to the `ItemMetadata` fragment, `resolvedCategories` on the response type, and `TaxonomyMode` on options are purely additive.
- **FR-008**: The SDK MUST export the `ResolvedCategory` type from the public API so TypeScript consumers can reference it without casting. The exported type uses `name: string | null` to accommodate unresolvable terms.
- **FR-009**: Tests MUST cover: (a) query generation — `categories` is present in emitted `ItemMetadata` fragment when taxonomy is enabled, absent when disabled; (b) `TaxonomyMode` detection — `'automatic'` correctly probes and toggles; (c) response type — `_metadata.categories` is correctly typed `string[]`; (d) hierarchy resolution — `_metadata.resolvedCategories` contains correct breadcrumb data when `resolveCategories: true`; (e) cache key — `taxonomyEnabled` is included in the cache key.
- **FR-010**: When `TaxonomyMode` is `'automatic'` (default), the SDK MUST detect whether the Graph schema supports taxonomy via a `__type` introspection probe (e.g., `taxonomyType: __type(name: "_TaxonomyTerm") { __typename }`) added to `METADATA_QUERY_BODY` in `queries.ts`, following the existing DAM detection pattern (`damAssetType: __type(name: "cmp_Asset")`). The probe result is consumed in `getContentMetaData()` in `operations.ts` to resolve `TaxonomyMode` → `taxonomyEnabled: boolean`, following the same flow as `DamMode` → `damEnabled` via `fragmentContext()` in `options.ts` and `createQueryContext()` in `queryUtils.ts`.
- **FR-011**: When hierarchy resolution is enabled, resolved category labels MUST be returned in the same locale as the content item being fetched. If a term has no translation for the requested locale, the default-locale label is returned as fallback (matching Graph API behavior). **Locale propagation**: The locale used for the taxonomy resolution query (whether inline or batched `_TaxonomyTerm`) MUST be derived from the same locale used by the content operation — i.e., the locale from the `GraphReference` (parsed from the graph URI's `loc` parameter) for `getContent`, or from `PreviewParams.loc` for `getPreviewContent`. For `getContentByPath`, no explicit locale is available at request time (the operation takes only a path string); in this case the SDK uses each returned content item's `_metadata.locale` from the response to resolve hierarchy labels per-item. This is an exception to the general prefer-request-time-locale principle — it is acceptable because `getContentByPath` can return items in multiple locales, and the response locale is the authoritative locale for each item.
- **FR-012**: The query cache key in `withQueryCaching` (built by `createCacheKey()` in `cache.ts`) MUST include a `taxonomyEnabled` component in the key array (alongside existing `damEnabled` and `formsEnabled`) to prevent stale cache hits when `TaxonomyMode` changes the query shape. Additionally, `resolveCategories` MUST be included in the cache key, since it changes the final response shape (adds `resolvedCategories`). **Architecture note**: `taxonomyEnabled` fits naturally into `QueryContext` (alongside `damEnabled`/`formsEnabled`) and flows through `createCacheKey()` as-is. However, `resolveCategories` is an operations-layer option not currently part of `QueryContext`. To include it in the cache key, either (a) add `resolveCategories` to `QueryContext` as an optional field, or (b) implement a separate operations-level cache wrapper that accounts for response augmentation options. The planning phase should decide which approach to use. **Clarification**: The cache operates on the final augmented response (after hierarchy resolution), not just the raw GraphQL response. When `resolveCategories` is `true`, the cached entry includes the resolved hierarchy data, so a subsequent call with the same content key but `resolveCategories: false` must not return resolved data from cache (and vice versa). **Cache staleness for hierarchy data**: The cache does NOT independently track taxonomy term mutations (renames, restructures). Resolved hierarchy data is cached with the same TTL as the content response. If a taxonomy term is renamed on the CMS side, stale hierarchy labels may be served until the cache entry expires or is invalidated by a content change. This is acceptable — the SDK's cache is a short-lived query cache, not a long-lived data store. If stricter freshness is needed, the consumer should disable caching or reduce TTL.

### Key Entities

- **Category Term URI**: A string identifier assigned to content in CMS that references a taxonomy term. Returned as part of `_metadata.categories` (selected via the `ItemMetadata` GraphQL fragment spread into `_metadata`). Always `string[] | undefined`.
- **ResolvedCategory**: Exported TypeScript type: `{ uri: string; name: string | null; path: Array<{ uri: string; name: string | null }> }`. `name` is `string | null` to accommodate deleted/unresolvable terms. `path` is the full breadcrumb including the term itself as the last element. Populated on `_metadata.resolvedCategories` only when `resolveCategories: true` is passed to the operation.
- **Taxonomy Hierarchy**: The parent-child chain from the taxonomy root down to the category term itself, represented as a flat ordered array (breadcrumb) in `ResolvedCategory.path` — the term itself is always the last element. Labels are localized to the content item's locale, with default-locale fallback.
- **Content Item Metadata**: The `ItemMetadata` GraphQL type (a subtype of `IContentMetadata`), accessed via `_metadata { ...on ItemMetadata { ... } }` in generated queries. Extended with `categories` in this feature (in `baseTypeUtil.ts`). In the SDK's TypeScript layer, `InferredItemMetadata` in `infer.ts` is extended with `categories` (a GraphQL-sourced field), flattened into `_metadata` via `Partial<InferredItemMetadata>`. Note: `resolvedCategories` is NOT placed on `InferredItemMetadata` because it is SDK-side augmentation, not a GraphQL field. The exact type mechanism for surfacing `resolvedCategories` on `_metadata` (e.g., a separate augmentation type intersected into `InferredContentMetadata`, or post-hoc type widening in the operations layer) should be decided during planning.
- **TaxonomyMode**: A tri-state option type (`'automatic' | 'on' | 'off'`) controlling whether the SDK includes taxonomy fields in generated queries. Defined in `options.ts` on `GraphFragmentOptions` as the `taxonomy` field (following the `DamMode` naming convention: `DamMode` type → `dam` field; `TaxonomyMode` type → `taxonomy` field. Note: Forms does not follow this pattern — it has no user-facing mode type or field on `GraphFragmentOptions`). Resolved to `taxonomyEnabled: boolean` via `fragmentContext()` and `createQueryContext()`.

### Developer API Surface — Usage Example

Taxonomy configuration spans two layers. `TaxonomyMode` controls **query generation** (fragment-level — whether `categories` is selected at all), while `resolveCategories` controls **response augmentation** (operation-level — whether the SDK resolves hierarchy after the query). Example:

```ts
// Layer 1: Fragment options (typically set once at SDK init)
const client = createClient({
  // ...
  taxonomy: 'automatic', // default — probes schema; or 'on' / 'off'
  dam: 'automatic',
});

// Layer 2: Operation options (per-call)
// Locale is part of the reference (graph URI), not the options bag
const reference = 'graph://cms/Page/abc123?loc=en';
const content = await client.getContent(reference, {
  resolveCategories: true, // opt-in to hierarchy resolution
});

content._metadata.categories;         // string[] | undefined — always available when taxonomy enabled
content._metadata.resolvedCategories; // ResolvedCategory[] | undefined — only when resolveCategories: true
```

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of content fetched through the SDK's standard methods includes `_metadata.categories` when taxonomy is enabled and categories are assigned in CMS — no manual query patching needed.
- **SC-002**: Developers can access category hierarchy via `_metadata.resolvedCategories` directly from the SDK response (with `resolveCategories: true`) without writing any additional GraphQL queries.
- **SC-003**: Existing SDK consumers upgrading to the new version experience zero breaking changes — all current queries and response handling continue to work unchanged.
- **SC-004**: TypeScript consumers get full autocompletion and type checking for `_metadata.categories` (`string[] | undefined`), `_metadata.resolvedCategories` (`ResolvedCategory[] | undefined`), and the `ResolvedCategory` type without requiring type casts.
- **SC-005**: Category hierarchy resolution adds no more than one additional network round-trip **per content fetch call** compared to a fetch without `resolveCategories` (ideally zero — embedded in the same query).

## Assumptions

- **[MUST VERIFY IN PLANNING — impacts FR-001, FR-002, FR-003, FR-010]** The Optimizely Graph API already exposes `categories` on the `ItemMetadata` GraphQL type (a subtype of `IContentMetadata`). The exact field name, type structure, and whether it is on `ItemMetadata` vs. `IContentMetadata` MUST be verified by inspecting the Graph schema before implementation. If the field name or location differs, FR-001 (fragment placement), FR-002 (type definition), FR-003 (empty/undefined semantics), and FR-010 (introspection probe target) must be adjusted accordingly.
- **[MUST VERIFY IN PLANNING — impacts FR-004, FR-005, FR-006, FR-011, FR-012]** The Graph API provides a mechanism to resolve taxonomy hierarchy (parent terms, labels) either inline within the content query (e.g., selecting `parent` fields on category terms) or via a batch-friendly `_TaxonomyTerm` query — not requiring per-term individual queries. The specific mechanism MUST be confirmed during planning by running a test query against a taxonomy-enabled Graph instance. If neither mechanism exists, FR-004 and FR-005 degrade to "resolvedCategories always undefined" and User Story 2 is descoped. FR-006 (batching), FR-011 (locale propagation), and FR-012 (cache key for resolveCategories) become N/A in that case.
- Taxonomy/category support (part 1 of Taxonomy in Optimizely Graph) is already shipped on the CMS side and available in the Graph schema — but some instances may not have it enabled, so the SDK must handle graceful omission via `TaxonomyMode` schema detection.
- Category term URIs are stable string identifiers that do not change once assigned (though the term itself may be renamed or moved in the taxonomy tree).
- The SDK query caching mechanism (`withQueryCaching` / `createCacheKey()` in `cache.ts`) will require a new `taxonomyEnabled` component in the cache key array, following the existing `damEnabled`/`formsEnabled` pattern.
- Taxonomy terms are localizable in CMS, and the Graph API returns localized labels when queried with a locale parameter. When no localized label exists, the default-locale label is returned.
